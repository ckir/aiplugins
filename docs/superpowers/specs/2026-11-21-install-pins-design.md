# Install-document pins and root README coverage: keeping them current

Status: design. The approach (generate and gate the pins, not a one-off refresh and not "latest at install time")
was chosen by the owner on 2026-11-21 after an agy consult. The owner then put two things into this change: the
root README fix with its check, and the stale pins in the agy and qwen plugin READMEs. The line-level plan waits
for the owner's review of this spec.

## 1. Problem

Users install a plugin by following a document on `main`: an OpenCode plugin through its `INSTALL.md` (an agent is
told to fetch `https://raw.githubusercontent.com/ckir/aiplugins/refs/heads/main/opencode/plugins/<plugin>/INSTALL.md`),
an Antigravity or Qwen plugin through its `README.md`. Those documents pin release versions by hand, and nothing
bumps them on release. Three things on `main` are out of date:

1. **OpenCode `INSTALL.md` pins.** Each of the seven `opencode/plugins/*/INSTALL.md` files carries `VERSION=` (the
   plugin's own release) and, for the four plugins with a binary from a Claude Code sibling, `CC_VERSION=`:

   | Plugin | Doc says | Current release |
   |---|---|---|
   | `repo-tasks-mcp-opencode` | 0.1.0 / cc 0.1.0 | 0.2.0 / cc 0.2.0 |
   | `opencode-ctl-mcp-opencode` | 0.1.0 / cc 0.1.0 | 0.2.1 / cc 0.2.0 |
   | `rtk-mcp-opencode` | 0.7.3 / cc 0.8.0 | 0.10.1 / cc 0.8.1 |
   | `re-ghidra-mcp-opencode` | 0.7.3 / cc 0.8.0 | 0.10.1 / cc 0.9.1 |
   | `todov2-opencode` | 0.3.0 | 0.6.1 |

   | `aiplugins-devtools-opencode` | 0.1.0 | 0.5.0 |

   Six of the seven files also repeat the version in header prose ("`0.7.3` / `0.8.0` are current as of this

2. **Antigravity and Qwen README pins.** Seven plugin READMEs carry a literal release URL (and, in three, a prose
   claim). The Qwen ones still use the frozen lockstep tag `releases/download/v0.7.2/...` instead of the

   `repo-user-guide-opencode` are missing from both. The generated site is not affected (`scripts/gen-site.sh`

Every "current" tag in the tables exists as a published, non-draft GitHub release carrying the asset name the
document uses (measured with `gh release view`).

## 2. Goals and non-goals

Goals: after this change `main`'s install documents point at the current release; they cannot drift again without
CI failing; and the root README lists every OpenCode plugin.

Non-goals:
- No `releases/latest` and no install-time lookup. The repo rule is tag-pinned URLs only
  (`docs/superpowers/plans/2026-10-05-opencode-agy-first-class-bundles.md:16`): GitHub's `latest` is repo-wide,
  so one package's release displaces another's, and installs would stop being reproducible.
- The `@opencode/plugin` pin, which `scripts/bump-opencode-plugin.sh` and `scripts/check-opencode-wiring.sh`
  check 9 already own.
- Version numbers that are not a plugin release pin, such as "As of Qwen Code v0.22.3" in the qwen READMEs.
- Root `README.md` coverage for hosts other than OpenCode (not examined), and any change to the generated site.

## 3. Decisions

| Fork | Chosen | Rejected, and why |
|---|---|---|
| Scope | Refresh now, plus a script that rewrites the pins and a gate that checks them | A one-off refresh goes stale at the next release, as it did this time. |
| Mechanism | The pins script, run with `--write` by `.github/workflows/release-refresh.yml` and checked in CI | release-please `extra-files`: the `packages` table of `release-please-config.json` is generated by `scripts/gen-release-please-packages.sh` and CI checks it, so a hand edit fails; and `extra-files` cannot carry the cross-component `CC_VERSION`. |
| Version oracle | The host manifests (`package.json`, `plugin.json`, `qwen-extension.json`, the sibling `plugin.json`) | `.release-please-manifest.json`: `scripts/check-release-manifest.sh:22-23` reserves its values for release-please. |
| `CC_VERSION` timing | Refresh both pins in the same pass | Waiting for the dist build to finish would need a second bot commit to `main` and a non-offline CI check. |
| One script or two | One script, two pin styles | Two scripts would duplicate the registry walk, the CRLF handling and the wiring. |
| Script name and default mode | `scripts/check-install-pins.sh`: checks by default, `--write` rewrites | `gen-install-pins.sh`: `scripts/check-gate-wiring.sh` discovers only `scripts/check-*.sh` (its header and line 153), so a `gen-` script could be dropped from `just check` and from CI with that gate still green. `gen-marketplaces.sh` has this gap today; this change does not widen it. |

The `CC_VERSION` timing is not a cross-PR race: `release-please-config.json` has no `separate-pull-requests`,
so when an opencode plugin and its sibling `-cc` both bump, they arrive in one release PR; when only one bumps,
the other's pin is already its released version.

## 4. Design

### 4.1 Pin contract

Two styles, by document kind:

- **Variable-line style (OpenCode `INSTALL.md`).** `VERSION=<x.y.z>` and, where present, `CC_VERSION=<x.y.z>` in
  Step 2 are the version pins, and the URLs use `$VERSION` and `$CC_VERSION`, so a document normally carries
  each version once. A file has exactly one `VERSION=`
  line at the start of a line, and exactly one `CC_VERSION=` line if and only if the plugin's `opencode.jsonc`
  declares a local MCP server (the binary that comes from the Claude Code sibling's release). The existence of a
  `claude-code/plugins/<family>-cc` folder is not the test: `aiplugins-devtools-cc` and `repo-user-guide-cc`
  exist and ship no binary, and their OpenCode plugins have no `CC_VERSION=` (measured: the four plugins with
  a local MCP server are `rtk`, `re-ghidra`, `opencode-ctl` and `repo-tasks`). The literal-tag rule below also
  applies to these files: a hardcoded `<plugin>-v<x.y.z>` or `<family>-cc-v<x.y.z>` token, or a
  `releases/download/` URL whose tag is neither `<plugin>-v$VERSION` nor `<family>-cc-v$CC_VERSION`, must equal the
  current version, so a hardcoded stale URL cannot hide behind a correct `VERSION=` line. A literal someone writes
  anyway is a second pin: the script keeps it equal to the first, and `--write` rewrites it in place, so it cannot
  go stale at the next release. `$VERSION` stays the convention. No INSTALL.md has one today (measured).
- **Literal-tag style (agy and qwen `README.md`).** Every `releases/download/<tag>/<asset>` URL whose asset name
  starts with `<plugin>-`, and every bare tag token `<plugin>-v<x.y.z>` in the prose, must carry the plugin's
  current version. The legacy form `releases/download/v<x.y.z>/<plugin>-...` is migrated to
  `releases/download/<plugin>-v<version>/<plugin>-...`.

Prose that repeats a number in a way the script cannot find (a backticked bare version in a sentence) is
reworded once, by hand, to point at the URL or Step 2 instead. The instruction to agree the versions with the
user first stays. A guard fails on the phrase `current as of this writing` in any document the script covers;
it catches the one known wording, not a rewording of it, and the spec does not claim more. It matches after, in this
order, removing a trailing carriage return from each line (no covered document has one today, but the repo's own
`bump-opencode-plugin.sh` selftest requires CRLF files to survive), dropping from each line a leading run of spaces,
one `>` and one optional space, joining the lines with single spaces, and collapsing runs of whitespace. The
match is the exact lowercase phrase and does not look through markdown emphasis, because the guard claims the
one known wording and no more. It joins lines because the phrase wraps
across lines and, in an INSTALL.md header, across blockquote lines: measured, `repo-user-guide-opencode/INSTALL.md`
lines 9-10 and `aiplugins-devtools-opencode/INSTALL.md` lines 10-11 hold it wrapped, and a one-line `grep` finds
neither.

### 4.2 `scripts/check-install-pins.sh [--write | --selftest] [--root DIR]`

- Walks `registry_plugins` for `opencode`, `antigravity` and `qwen` (`scripts/lib/registry.sh`).
- The plugin's version comes from its own manifest: `package.json` for OpenCode, and
  `registry_manifest_path <agent> <plugin>` (`plugin.json`, `qwen-extension.json`) for the other two.
- `CC_VERSION` (required exactly when `opencode.jsonc` declares a local MCP server, as in 4.1; the check uses the
  filter `scripts/check-opencode-wiring.sh:98` uses, `.mcp.servers // {} | .[] | select(.type == "local")`;
  `opencode.jsonc` is kept comment-free so `jq` reads it (that script's check 3), and a skills-only plugin has no
  `opencode.jsonc` at all, which counts as no local MCP server) is `.version` of
  `claude-code/plugins/<family>-cc/.claude-plugin/plugin.json`, where the sibling is the plugin name with the
  `-opencode` suffix replaced by `-cc`.
- Rewrites only what 4.1 names, byte for byte otherwise, preserving CRLF the way
  `scripts/bump-opencode-plugin.sh` does. A URL for another plugin's asset, or a non-release URL, is untouched.
- Fails loudly (exit 1, names the file) on: a missing or duplicated `VERSION=` line, a missing `CC_VERSION=` line
  where 4.1 requires one, a `CC_VERSION=` line where it does not, a `CC_VERSION=` line with no sibling manifest, an unreadable or non-semver version, and a census of zero pins
  checked overall. It never skips silently. A README with no release URL is valid and counted as zero.
- With no flag it is a check: it rewrites nothing, exits 1 if any document would change, prints which differ and
  how many pins it checked. It sorts what it found into two kinds: a stale pin, which `--write` fixes, and a
  structural violation (a missing or duplicated line, a bad version, the `current as of this writing` guard),
  which needs a hand edit. It names the `--write` command only when it found a stale pin, and it names the edit
  for each structural violation, so a contributor is never sent to a command that cannot help. When a tree has
  both kinds, `--write` cannot succeed until the structural ones are fixed (it is all-or-nothing), so the message
  lists the structural edits first and says `--write` applies after them. `--write` rewrites.
- `--write` is all-or-nothing: it validates every document first and writes none if any fails, so a failure
  never leaves a half-rewritten tree for the workflow to commit.

### 4.3 Wiring

- `.github/workflows/release-refresh.yml` runs `check-install-pins.sh --write` after `scripts/gen-marketplaces.sh`
  and adds `opencode/plugins/*/INSTALL.md`, `antigravity/plugins/*/README.md` and `qwen/plugins/*/README.md` to its
  `git add` list. The pins step is `continue-on-error` with an id, and a last step fails the job when it failed,
  so a pins failure still lets the marketplace refresh commit and still turns the job red. That last step prints
  an `::error::` line that names the pins step, so the run summary points at the real failure and not at a
  bare `exit 1`. The refresh commit is
  `chore:`, which release-please does not treat as releasable.
- `.github/workflows/ci.yml` gets a step running the default (check) mode and a step running `--selftest`, beside
  the existing `gen-marketplaces.sh --check`.
- `Justfile` gets two recipes (the check, and the selftest) added to the `check` recipe's list.
  `scripts/check-gate-wiring.sh` then requires the script to be named in the `Justfile` and in CI, because its
  name matches `check-*.sh`; its own selftest covers that rule, so this change adds no case to it.
- `docs/PLUGIN_GUIDELINES.md` section 3.4 (Kind C) and the sections for the other kinds say the install-document
  pins are generated, not hand-edited, and name the script in the "what fails if you skip it" tables.

### 4.4 Root README coverage

- Add the three missing rows to the OpenCode table and the three missing raw-URL bullets to the list at
  `README.md:50-55`, in the same form as the existing ones. Each row's "Copies" and "Binary staging" cells are
  written from that plugin's own INSTALL.md, not from memory; the plan step verifies each cell against it.
- Add `scripts/check-readme-coverage.sh [--root DIR | --selftest]`, a new gate. It reads only the
  `## Installing` section of `README.md` (from that heading to the next `## ` heading), because `README.md` links
  every OpenCode plugin a second time in its repository-structure list (`README.md:157-164`), and a check that
  accepted a link anywhere in the file would pass today with the gap it exists to catch. For every registry
  OpenCode plugin it requires, inside that section: a table row linking `opencode/plugins/<plugin>/`, and a
  bullet carrying the exact raw INSTALL URL; and it requires the `INSTALL.md` file itself. In the other
  direction, a row or URL in that section naming an OpenCode plugin that is not in the registry fails.
  Matching is by substring on the line, so formatting never matters. A *row* is a line of the section that starts
  with `|` and contains `](opencode/plugins/<plugin>/)` (the real rows put the name in backticks inside the link
  text, `README.md:38`). A *bullet* is a line that starts with `- ` and contains
  `https://raw.githubusercontent.com/ckir/aiplugins/refs/heads/main/opencode/plugins/<plugin>/INSTALL.md` as a
  substring (the real bullets wrap the URL in backticks, `README.md:52`). The section ends at the next line that
  starts with `## `. Lines inside a fenced code block do not count as a row or a bullet (the real section has one,
  `README.md:19-21`). The registry list comes from `registry_plugins opencode` (`scripts/lib/registry.sh`), with
  `REGISTRY` set to `<DIR>/agents.json` under `--root DIR`, the way that file's own selftest sets it (`:99`).
  It is a separate script because `scripts/check-opencode-wiring.sh` has no selftest harness
  (it runs checks 1 to 9 and exits), and a gate with no way to prove it rejects a defect is the failure this
  repo's other gates avoid. Its `Justfile` and CI wiring follow the same two-recipe, two-step shape as 4.3, and
  `scripts/check-gate-wiring.sh` enforces it by name.

### 4.5 One-time catch-up

The first `--write` run, committed with the README fix and the header-prose rewording, brings the 14 documents to
the tables in section 1. The hand rewording comes first and is committed before that run, because the
`current as of this writing` guard makes `--write` abort until every occurrence is gone. Measured, there are ten
occurrences in eight documents: the six INSTALL.md headers and two agy READMEs (`rtk-mcp-agy/README.md:38`,
`re-ghidra-mcp-agy/README.md:100`), plus a second sentence in the step body of `rtk-mcp-opencode/INSTALL.md:57`
and `re-ghidra-mcp-opencode/INSTALL.md:67`; two of them are the wrapped ones above. 

Work happens on a fresh branch off `origin/main`, not on `fix/dist-macos-runner` (that branch's fix already merged
as PR #162). It lands as two commits, in this order. First, the hand rewording of the ten occurrences and the
root README rows. Second, the two scripts, their `Justfile`, CI and workflow wiring, and the first `--write` run.
The second is one commit because `scripts/check-gate-wiring.sh` requires every `scripts/check-*.sh` to be run by a
`Justfile` recipe that `just check` reaches (its header, point 1), so a script cannot land before its wiring.

## 5. Testing

- `--selftest` builds a scratch tree and asserts, case by case:
  - Variable-line style: a stale pin is rewritten; a fresh tree is a no-op and a second run is idempotent;
    the default mode fails on a stale tree and writes nothing; a missing sibling manifest, a missing `VERSION=` line, a
    duplicated `VERSION=` line, a `CC_VERSION=` line with no sibling, a plugin with a local MCP server and no
    `CC_VERSION=` line, a skills-only plugin with a `-cc` folder and a `CC_VERSION=` line, and a non-semver
    version each fail with the file named; a file without `CC_VERSION=` gets none added; an absent `opencode.jsonc`
    means no `CC_VERSION=` is required; a hardcoded stale `<plugin>-v<x.y.z>` URL in an INSTALL.md that has a
    correct `VERSION=` line fails in the default mode and is rewritten by `--write`; a structural violation
    does not print the `--write` command, a stale pin does; one bad document among several makes `--write` change none of them.
  - Literal-tag style: a stale per-package tag is rewritten in the URL and in the prose token; the legacy
    `download/v<x.y.z>/` form is migrated; every occurrence in one file is rewritten; a URL for another plugin's
    asset and a non-release URL are untouched; a README with no URL is a no-op; the `current as of this writing`
    guard fails.
  - Both: CRLF survives; the zero-census failure fires on an empty tree.
- The guard has a case for a wrapped, blockquoted occurrence in the shape of `repo-user-guide-opencode/INSTALL.md:9-10`,
  and the section scan has a case for a row that sits inside a fenced block and must not count.
- Fixtures are copies of real document shapes, not idealised strings. The selftest includes: a README bullet with
  the URL in backticks and a table row whose link text is in backticks (`README.md:38,52`); a qwen README with
  the same URL in a prose line and in a table cell (`qwen/plugins/rtk-mcp-qwen/README.md:34,48`); an agy README
  with a backticked prose tag followed by punctuation (`antigravity/plugins/aiplugins-devtools-agy/README.md:21`);
  and an INSTALL.md whose prose names `rtk-mcp-cc-v$CC_VERSION`
  (`opencode/plugins/rtk-mcp-opencode/INSTALL.md:102`), which must be left untouched and not reported as a
  non-semver version.
- Mutation run, by hand, one line-level mutant per guard (drop the duplicate check, drop the sibling check,
  change the anchor, drop the legacy migration, drop the CRLF handling, make the default mode write); each must turn a
  named selftest case red.
- `check-readme-coverage.sh --selftest` builds fixture trees through `--root` and covers: a plugin missing from
  the table, missing from the URL list, a URL with a wrong path, a row for an unregistered plugin, a registered
  plugin with no `INSTALL.md`, and a plugin linked only in a section other than `## Installing` (the case that
  proves the section scoping; it must fail).
- The repo's own gate stays as it is: `just check` and the CI jobs, with no stricter flags. The plan runs
  `just footprint` and `just footprint-budgets` after the catch-up, because the figures live in README regions
  and the version strings change length (for example `0.1.0` to `0.10.1`); the spec expects no change but the
  plan must measure it.

## 6. Accepted trade-offs

- After a release PR merges, `main`'s documents name the new tag a few minutes before the dist build has uploaded
  every binary. The marketplace manifests already work this way. The documents' existing "if a download fails,
  check the releases page" instruction covers it.
- `CC_VERSION` is the sibling's manifest version, which is the version release-please tags. If a sibling's tag
  were ever cut by hand with a different number, the pin would be wrong; the repo forbids hand tags (`HACK.md`).
- Migrating the qwen READMEs off the legacy `v0.7.2` tag changes what a reader downloads (the 0.8.0 extension, not
  the frozen 0.7.2 one). That is the intent, since 0.7.2 is the lockstep line the repo retired.

## 7. Out of scope, for later

Root `README.md` coverage for Claude Code, Antigravity and Qwen plugins, and any change to how the generated site
is built.

## 8. Stand-downs

- `DISCARDED-BELOW-FLOOR`: a non-fast-forward rejection of the refresh push when release-please force-pushes the
  branch mid-run (`.github/workflows/release-refresh.yml:79`, a plain push). Unreachable as a stall because that
  force-push is itself a `pull_request` event that retriggers the workflow, which regenerates on the new head
  (the retrigger and convergence stated at `.github/workflows/release-refresh.yml:13-14` and `:42-43`). The
  marketplace step already lives with the same transient; this change adds no new push.

- `DISCARDED-BELOW-FLOOR`: the `git add` globs for the agy and qwen READMEs could stage a stray working-tree
  change. Unreachable because the job starts from a fresh checkout of the PR head
  (`.github/workflows/release-refresh.yml:45-49`) and nothing but the two deterministic generators writes to the
  tree before the `git add` at `:68`; a README with no release URL is not rewritten, so it is not modified.
