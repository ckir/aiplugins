# opencode-ctl-mcp Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the `opencode-ctl-mcp` plugin (engine crate `shared/opencode-ctl`, four host fronts, pairing launcher, two skills) so Claude Code, Qwen Code, Antigravity and OpenCode can drive an OpenCode worker session through 20 typed MCP tools.

**Architecture:** One library crate owns everything (`Engine<T: Transport, C: Clock>` wrapping an rmcp `#[tool_router]` server, a `CliTransport` that shells out to `opencode api`, the OpenAPI gate, the pairing contract and the launcher); four thin per-host binaries call `opencode_ctl::cli::dispatch`. The wait/tool state machines are built and tested first against an in-process `FakeTransport`, then the real CLI transport is proven against a mock `opencode` binary, then host guards, pairing, doctor, launcher, fronts and release wiring land in that order. A lifted `shared/proc-guard` crate carries the process-group / job-object kill guard shared with `ghidra-worker-ctl`.

**Tech Stack:** Rust 1.99 (stable; `std::fs::File::lock` needs 1.89+), rmcp 3.1 workspace dependency (locked 3.5.1), tokio, serde/serde_json, schemars 1.0, tracing + tracing-appender, lru, sha2, uuid, thiserror, proptest (dev); `nix` (unix) and `windows` (windows) cfg-gated; bun for the OpenCode front's tests. No new crates.

**Spec:** `docs/specs/2026-10-18-opencode-ctl-mcp-design.md` (APPROVED, panel done at 1e5f9c7). Every contract below comes from it. Decisions this plan makes where the spec left a choice are collected under **Plan decisions**; a task that applies one says "(plan decision N)".

## Plan decisions

1. Process guard: lift `shared/ghidra-worker-ctl/src/job_object.rs` into a new crate `shared/proc-guard` (AGY-FIRST aligned).
2. Qwen front stays OUTSIDE the footprint gate in v1 with a HACK.md note; `tools/plugin-footprint/src/manifest.rs:16` defers Qwen manifests (AGY-FIRST aligned on measurement).
3. CLI stdout temp files live under `<ctl home>/stdout/<pid>-<starttime>/` so `gc` and `serve` can sweep them.
4. The doctor skill reads a machine report from the `doctor-json` subcommand instead of running checks in prose.
5. `OpencodeCtlServer` and `Engine` are generic over `Transport` and `Clock`; rmcp-macros 3.5.1 appends the router method inside the user's impl block (`tool_router.rs:91`), so generics are preserved.
6. `FakeTransport`, `TestClock`, `FakeProbe` and the mock binary's logic live in a public `opencode_ctl::testing` module so the fronts' tests reuse them without extra dependencies.
7. The eight committed skill copies are produced by `emit-opencode-ctl-skills` from the cc binary with `--host`; the recipe lands when all four front directories exist (Task 23).
8. The shipped `opencode.jsonc` snippet uses a RELATIVE `./bin/...` command like both OpenCode siblings; a committed file cannot carry an install path. INSTALL.md rewrites it to an absolute path and says why (spec Layout wording "ABSOLUTE command" applies to the merged copy).
9. `pair` titles use UTC `HH:MM` (std has no local time and no time crate is allowed); the title is `pair <basename> <HH:MM>Z`.
10. A `serve` that cannot open its log file logs a warning to stderr and keeps serving without a file log (an MCP server that dies on a read-only home takes the OpenCode-host plugin down with it); every other unwritable file is `IO_ERROR`.
11. The TUI wrapper carries `OPENCODE_SERVER_PASSWORD` as an `export` line baked into the 0700 wrapper script when `server_url` is set and the variable is present at launch (a terminal tab does not inherit the launcher's environment; the wrapper is the only vehicle). The owner may veto (Open items). The wrapper also unsets `OPENCODE_PASSWORD` beside it, because the CLI reads that variable first (`packages/cli/src/env.ts:10-13`; panel round 9).
12. The cc front has no `src/lib.rs`; host-specific paths live in `Host`.
13. The mock's per-key sequence counters and argv log live in `MOCK_OPENCODE_STATE_DIR` (a per-test temp dir), never in the fixture tree.
14. `agy-validate` runs `agy plugin validate --strict` on the opencode-ctl agy front only (the re-ghidra agy front fails the validator today; tracked as github issue 101).
15. The `session.diff` cache key is `(session, from, to, context)`: the spec names `(session, from, to)`, and `context` changes the patch text, so a stricter key is the only correct one.
16. The reachability probe (`opencode service status`) runs only on the UNMAPPED failure path (exit != 0, no `_tag` on stdout, no matched stderr line); a failure that carries a `_tag` is mapped by the tag and never probed.
17. `ProcessProbe` (the trait), `SystemProbe` and `FakeProbe` land in Task 3 so the `Engine` can hold a probe from Task 7 on; pairing-specific liveness logic lands in Task 15.
18. Exclusive claims (`write_record_new`, `resume-lock`, wrapper-generation claims) are published atomically: write a temp file with the full content, then `hard_link` it to the final name (fails when the name exists), then delete the temp; readers never see an empty claim. Where `hard_link` is unsupported by the volume, `claim_file` falls back to `create_new` (Task 15; panel round 9), accepting the empty-read window there.
19. `opencode service status` prints the service URL when running and the word `stopped` when not, exit 0 either way (`packages/cli/src/commands/handlers/service/status.ts:13`, measured: `http://127.0.0.1:49374`); "running" therefore means exit 0 and trimmed stdout != `stopped`. `opencode --version` prints `opencode v2.0.32` (measured); versions are parsed by `parse_cli_version`, which strips an optional `opencode ` and `v` prefix.
20. Logging has two scopes: `serve` installs the global subscriber once (`try_init`); the launcher subcommands, `gc` and every test use a scoped subscriber (`tracing::subscriber::set_default`) whose guard lives in the returned handle, so several logs can be opened in one process. `set_default` is per thread, so every front binary's `main` is `#[tokio::main(flavor = "current_thread")]` (Tasks 20-22): all tasks a subcommand spawns run on that one thread and stay under the scoped subscriber; `serve` is unaffected (it uses the global scope and rmcp's stdio transport needs no worker threads). A test pins the mechanism: a task spawned under the scoped subscriber writes to the scoped log file; the attribute itself is spelled out in Tasks 20, 21 and 22 (the sibling pattern files carry a plain `#[tokio::main]`, which must NOT be copied).
21. Service-down model, measured against the v2.0.32 CLI (supersedes the spec's `ECONNREFUSED` wording): a plain `opencode api ...` with no `--server` resolves the managed service through `Service.ensure`, which STARTS the service when none is healthy (`packages/cli/src/services/server-connection.ts:74-80`, `packages/client/src/effect/service.ts:45-49`), so in managed mode a stopped service is revived by the next tool call rather than reported; `service_status` therefore runs `opencode service status` FIRST and calls `server.info` only when it printed a URL, so it never starts the service it reports on (with `server_url` set it skips the local status call and asks `server.info` through `--server` directly, since the local service is not the target), and the `service_stop` description says "any later session tool restarts the service". The CLI never prints `ECONNREFUSED`; an unreachable `--server` target prints `Error: Could not reach server at <url>` on stderr (`server-connection.ts:96`), which maps to `SERVICE_DOWN`. The reachability probe (decision 16) runs only when `server_url` is unset; with `server_url` set an unmapped failure is `CLI_ERROR` as is.
22. Wire tags, measured: a synthetic id collision is answered as `ConflictError` with a message starting `Synthetic input ID conflicts` (`packages/server/src/handlers/session.ts:414-421`); `SyntheticConflictError` never reaches the wire. The launcher's exit-notice retry keys on that message.
23. Message rows, from the schema (`packages/schema/src/session-message.ts:75-77,213-218`): a `user` message carries top-level `text`; an `assistant` message carries `content: [...]` whose entries have `type` (`text`, `reasoning`, `tool`, ...) and `text`/tool fields; there is no `parts` key. Compaction and fixtures use these keys.
24. Lifecycle verbs with `server_url` set (panel rounds 7-8): `opencode service start|stop|restart` manage only the LOCAL managed service, never the `--server` target. `service_start` with `settings.server_url` set therefore makes NO lifecycle call and returns exactly the `service_status` result (the idempotent "ensure the service runs" contract is answered by the remote's `running`/`reachable`; nothing local can be started for it), so the driver loop ("`service_start` when it reports not running") and the launcher's step 1 keep working against a remote target; `service_stop` and `service_restart` with `server_url` set return `REFUSED_ON_HOST` ("server_url is set (<url>): the local lifecycle verbs cannot stop or restart that server; unset server_url to manage the local service"; agy round 8: the spec defines `INVALID_REQUEST` as the server's own 400/404 answer, spec Tools line 377, while `REFUSED_ON_HOST` is the refusal the driver skill routes to the doctor), checked together with the host refusal and before `CONFIRM_REQUIRED`, and record no lifecycle call. The launcher's step 1 skips `opencode service start` when `server_url` is set (no `would run: opencode service start` line in `--dry-run`) and still runs `gc`. The spec never addressed this configuration (owner item 6).

## Review Focus

Inputs the spec implies but no task's named test exercised at planning time; each gets the test named here, added to the owning task.

1. **A settings file saved with CRLF line endings** (Windows editor): keys must still parse; `settings_crlf_frontmatter` (Task 4).
2. **The service died but its registration file is still present**: in managed mode the next `opencode api` call restarts it (plan decision 21), so the failure the engine can see is a `Service.ensure` that cannot spawn (an unmapped stderr, then the probe says `stopped`) or, with `server_url`, `Could not reach server at <url>`; both must map to `SERVICE_DOWN`, not `CLI_ERROR`; `transport_dead_service_is_service_down` (mock mode `server.info:unreachable`) and `transport_probe_decides_service_down` (mock modes `server.info:unmapped` + `service.status:stopped`; plan decision 16) (Task 13).
3. **A `--param` value containing a newline or NUL**: refused with `INVALID_ARGUMENT` before any spawn; `hatch_param_name_prefix_and_value_rules` (Task 5) and `hatch_tool_rejects_newline_param_value` (Task 9).
4. **`OPENCODE_CTL_HOME` pointing at a path with spaces** (and the wrapper script baking it in): wrappers must quote it; `wrapper_quotes_home_with_space` (Task 18).
5. **A worker turn whose anchor message was removed server-side** (`session.revert` via the TUI): the marker search never finds the anchor; rule (iii) applies (the newest message's `time.created` is the clock, so the first page already satisfies the stop rule and the search costs one read) and the state is `running` then `stalled`; `wait_anchor_vanished_uses_newest_message_clock` (Task 10).
